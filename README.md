# ContentKita

30 hari content khas untuk restoran anda.

ContentKita turns a short restaurant profile into a 30-day social media content
plan — hook, caption, CTA, photo idea and (where it fits) a Reel idea for every
day. Built for Malaysian restaurant, cafe and kedai makan owners, in BM.

An owner signs up, answers four screens about their restaurant, uploads their
logo and menu, and gets a month of content written from what they actually
told us. They can copy any day, edit it, and regenerate a single day without
disturbing the other twenty-nine.

## Status: Milestone 3 — AI content engine

Content is generated by a real language model, through a server-side route.
The provider secret never reaches the browser. See
[Generation](#generation--libai-and-appapigenerate).

Two things are **not** verified end to end, and are listed honestly rather than
implied to work:

- **Logo and menu uploads.** The code, the client-side limits and
  `storage.rules` are all in place, but Cloud Storage has never been enabled on
  the Firebase project, so the bucket does not exist and no upload has ever
  succeeded. See [Enabling Storage](#enabling-storage).
- **Generation against the real OpenAI API.** The production key lives only in
  the Netlify site environment. Local runs exercise the full
  browser → route → provider path against a stand-in server
  (`scripts/stub-openai.mjs`), which proves the plumbing but not the prose.

## Getting started

```bash
npm install
cp .env.example .env.local   # then fill in from the Firebase console
npm run dev                  # http://localhost:3000
```

### Environment variables

| Variable | Where it lives | Secret? |
| --- | --- | --- |
| `NEXT_PUBLIC_FIREBASE_API_KEY` | `.env.local`, Netlify | No — see below |
| `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN` | `.env.local`, Netlify | No |
| `NEXT_PUBLIC_FIREBASE_PROJECT_ID` | `.env.local`, Netlify | No |
| `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET` | `.env.local`, Netlify | No |
| `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID` | `.env.local`, Netlify | No |
| `NEXT_PUBLIC_FIREBASE_APP_ID` | `.env.local`, Netlify | No |
| `OPENAI_API_KEY` | Netlify environment only | **Yes** |
| `OPENAI_MODEL` | optional, defaults to `gpt-4.1` | No |
| `OPENAI_BASE_URL` | optional, local development only | No |

The six `NEXT_PUBLIC_FIREBASE_*` values come from the Firebase console under
**Project settings → General → Your apps → Web app → SDK setup and
configuration**. They are the Firebase *Web* configuration: public by design,
shipped to every browser, and not a secret. Access is enforced by Firebase Auth
and by `firestore.rules`, never by hiding these strings. Without them the app
throws a `FirebaseConfigError` naming the missing variables; it does not fall
back to a local session.

`OPENAI_API_KEY` **is** a secret. It has no `NEXT_PUBLIC_` prefix on purpose —
that prefix inlines a value into the browser bundle. It is read in exactly one
file, `lib/ai/openai.ts`, which is marked `server-only` so an accidental import
from a client component fails the build instead of shipping the key. In
production it is set in the Netlify site environment and read at request time
by the route handler. It is never committed and never pasted into a source
file.

`OPENAI_BASE_URL` exists so the whole path can be exercised locally without
holding the production key. Point it at `scripts/stub-openai.mjs` and the app
behaves exactly as it does in production, minus the model. Leave it unset in
deployment.

## Testing

### Unit tests — `npm test`

186 tests, no framework, no network. `node --test` runs the `.ts` files
directly using Node's type stripping, which is why every import inside `lib/`
is relative and carries an explicit `.ts` extension: the `@/` path alias is a
bundler feature and does not resolve here.

The largest group is `lib/content/validate.test.ts`, which is the executable
form of the anti-hallucination promise — one test per class of invented fact
(price, promotion, testimonial, halal status, opening hours, award,
superlative, scarcity, guarantee, nutrition claim) plus the language rules.

### Live Firebase — `npm run verify:firebase`

Creates two throwaway accounts against the real project and proves that neither
can reach the other's data, that a signed-out client can reach nothing, and
that the Storage rules refuse the wrong type, the wrong size and another
owner's folder. It uses the real project rather than the emulator suite, which
needs a JVM this machine does not have — so a pass means the *deployed* rules
refuse these attempts, not that a mock said they would.

A Storage check that cannot run is reported as **skipped, and skipped still
fails the run**. Until the bucket exists, `verify:firebase` exits non-zero on
purpose.

### The owner journey — `npm run test:flow`

Requires `npm run build` first. Boots the production bundle and the provider
stub, drives a real Chrome over the DevTools Protocol (no Puppeteer or
Playwright dependency — see `scripts/lib/cdp.mjs`), and walks the whole journey
against the real Firebase project: sign up, four onboarding screens, upload
logo and menu, generate thirty days, open a day, copy the caption, regenerate
one day, confirm only that day changed, refresh, edit a caption, save, refresh,
sign out, sign back in, and confirm everything is still there.

A step that cannot run says **BLOCKED** with the reason and fails the suite. It
is never quietly counted as a pass. Today that is the two upload steps.

Each run creates a real account in the real project; it is recorded in
`scripts/.flow-accounts` (gitignored) and removed by `npm run test:cleanup`.

Run `npx firebase login --reauth` **before** the cleanup. `firestore.rules`
denies delete to every client, so the documents go through the Firebase CLI as
the project owner while the account still exists. With an unauthenticated CLI
the cleanup deletes the account, cannot delete the documents, and says so — and
those documents are then unreachable for good, because nothing can ever sign in
as that uid again.

### Responsive — `npm run test:responsive`

Every screen at 360px, 768px and 1280px, checking for sideways scrolling, tap
targets under 40px, text under 11px, and content hidden behind the fixed bottom
navigation. Onboarding is checked on a fresh account that has no restaurant
yet, because that is the only state in which the wizard is reachable.

## Routes

| Route | Screen | Access |
| --- | --- | --- |
| `/` | Landing page | Public |
| `/signup`, `/login` | Auth | Public; redirects a signed-in owner to `/dashboard` |
| `/onboarding` | 4-step restaurant profile wizard | Signed in, no restaurant yet |
| `/dashboard` | Today's content + the 30-day plan | Signed in, onboarded |
| `/content/[id]` | One day in full, with copy, edit and regenerate | Signed in, onboarded |
| `/profile` | Edit the restaurant, regenerate the plan, sign out | Signed in, onboarded |
| `/api/generate` | Server route to the AI provider | Signed in (Firebase ID token) |

`/dashboard`, `/content/[id]` and `/profile` share `AppShell` via the
`app/(app)/` route group. The landing page is deliberately outside every
provider, so a visitor who never signs in never downloads the Firebase SDK.

## Architecture

```
browser  ──►  /api/generate  ──►  OpenAI
   │            (server)
   └──────►  Firebase Auth / Firestore / Storage
```

The browser talks to Firebase directly, as a normal Firebase client — the
security rules are the boundary. It never talks to the AI provider. Everything
that costs money goes through one route handler that holds the only secret in
the system.

### Generation — `lib/ai/` and `app/api/generate/`

```
app/api/generate/route.ts   the only place the provider secret is used
lib/ai/verify.ts            who is calling, and whether they are within budget
lib/ai/request.ts           decodes and clamps the untrusted request body
lib/ai/prompt.ts            the system prompt, the truth rules, the JSON schema
lib/ai/generate.ts          plan and single-day generation, with one repair pass
lib/ai/openai.ts            the transport; reads OPENAI_API_KEY; `server-only`
```

The route, in order:

1. **Verify the caller.** The Firebase ID token is checked against Google's
   Identity Toolkit, which validates the signature, issuer, audience and
   expiry. This is deliberately *not* the Firebase Admin SDK: Admin would mean
   shipping a service-account private key into the deployment for one check
   that a public endpoint already performs.
2. **Check the budget.** 12 full plans and 120 single days per owner per hour,
   held in memory. A stuck client cannot run up a bill.
3. **Decode and clamp the body.** Field lengths, dish counts, day counts and
   enum values are all bounded. The owner id comes from the verified token, not
   from the body. Uploaded assets are reduced to a boolean — the route is told
   *that* a menu exists, never its URL.
4. **Generate, validate, repair once.** A month is one request; days that fail
   validation cost one more request for those days only. Never more than two.
5. **Answer in Malay.** The browser receives a code and wording safe to show an
   owner. The provider's own error text stays in the server log.

### Not inventing facts — `lib/content/brief.ts` and `validate.ts`

The single most important property of this product: it must never state
something the owner did not tell us. A restaurant owner who posts an invented
price, an invented promotion or an invented halal claim has a real problem.

Three layers, none of which trusts the previous one:

- **`brief.ts`** builds the restaurant brief. `known` holds only facts the
  owner supplied; `forbidden` names the gaps out loud — "you do not know the
  opening hours" — and each subject is licensed only by a field that actually
  contains it.
- **`prompt.ts`** puts both lists in front of the model, along with the exact
  strings it may quote (dish names, the promotion wording, the prices the owner
  themselves wrote) and the rule that governs everything else: if a fact is
  missing, write something that does not need it.
- **`validate.ts`** checks the output against the same rules and rejects days
  that break them. Rejected days are regenerated, not patched. The schedule —
  not the model's echo of it — decides each day's category and platform, so a
  promotion day cannot appear for a restaurant with no promotion.

### The content engine — `lib/content/`

```
types.ts           ContentGenerator, ContentPlan, ContentItem, RestaurantProfile
categories.ts      category metadata, platform affinity, video rules
schedule.ts        the 30-day rhythm, built from what the owner actually has
brief.ts           the restaurant brief: known facts, forbidden subjects
validate.ts        the anti-hallucination check applied to every response
ai-generator.ts    AiContentGenerator — talks to /api/generate, never to a provider
mock-generator.ts  MockContentGenerator — deterministic, offline, for tests
templates.ts       the offline copy, grouped by category
index.ts           getContentGenerator() — the single swap point
demo.ts            Warung Kak Ina, the sample restaurant on the landing page
```

`getContentGenerator()` always returns the AI engine. There is deliberately no
silent fallback to templates when the provider is unavailable: handing somebody
a month of generic copy while telling them it was written for their restaurant
would be worse than telling them generation failed. `MockContentGenerator`
stays for tests and offline verification.

### Firebase — `lib/firebase/`

```
config.ts         reads NEXT_PUBLIC_FIREBASE_*; throws FirebaseConfigError if short
client.ts         lazily initialises the app, Auth, Firestore and Storage
codecs.ts         RestaurantProfile / ContentPlan ↔ Firestore documents
data.ts           the reads and writes the app performs, keyed by uid
storage.ts        logo and menu upload, download URL, delete
upload-rules.ts   accepted types, size limits, safe object names
errors.ts         Firebase error codes → plain Malay the owner can act on
```

Three collections, each keyed by the owner's uid:

| Path | Holds |
| --- | --- |
| `users/{uid}` | `email`, `displayName`, `createdAt`, `updatedAt` |
| `restaurants/{uid}` | the restaurant profile, the asset pointers, + `ownerId` |
| `contentPlans/{uid}` | the 30-day plan, one document, + `ownerId` |

And two Storage folders:

| Path | Holds |
| --- | --- |
| `restaurants/{uid}/logo/…` | PNG or JPEG, up to 2MB |
| `restaurants/{uid}/menus/…` | PNG, JPEG or PDF, up to 5MB |

**The uid is the ownership boundary.** Because every document and every object
lives at a path keyed by the owner's uid, there is nothing for a client to
spoof — no `where("ownerId", "==", …)` query to forge. `ownerId` is stored for
readability, and the rules require it to *match the path* on write, so a forged
value is rejected rather than honoured.

### Security rules

`firestore.rules` denies everything by default, allows `get` (never `list`) and
`create`/`update` only to the signed-in owner of the path, and denies `delete`
outright — deleting an account is not a client operation.

`storage.rules` denies everything by default. The only writable area is
`restaurants/{uid}/…` with `{uid}` equal to the caller's own auth uid, and
content type and size are enforced server-side as well as in the browser. The
client-side checks exist to give the owner a clear message; the rules are what
actually stop a 500MB video.

```bash
npx firebase deploy --only firestore:rules --project <project-id>
npx firebase deploy --only storage --project <project-id>
```

### State — `lib/store.tsx`

`AppProvider` subscribes to Firebase Auth, loads the restaurant and the plan for
the current uid, and exposes them to the screens. Loaded data is tagged with the
uid it belongs to, and everything the components read is *derived* from that
record — so a sign-out or a switch of account cannot leave one owner's plan on
screen for another. localStorage is deliberately not consulted for anything.

Mutations read the current restaurant through a ref rather than through the
render closure. Onboarding saves the restaurant and generates the first plan
inside one click handler, with no render in between; a callback that closed over
`profile` would still be looking at the `null` from before the save.

Writes are explicit and never implicit: saving the restaurant does not touch the
plan, and regenerating a single day writes exactly that one day back.

### Auth — `lib/auth.ts`

`getAuthClient()` returns a `FirebaseAuthClient` behind the `AuthClient`
interface. There is deliberately **no mock implementation left in the file**: a
client that accepts arbitrary credentials is the kind of thing that survives
into production by accident, so the only way to run ContentKita is against a
real Firebase project.

Route protection has two independent layers. `components/auth-gate.tsx` decides
what a browser is allowed to *render*; the security rules decide what it is
allowed to *read*. The second is the boundary; the first exists so the
experience matches. The gate latches whether a restaurant existed when the
screen was opened, so completing onboarding does not unmount the wizard while it
is still generating.

### Design system

Tailwind v4, tokens defined in `app/globals.css` under `@theme`. No
`tailwind.config`. Primitives in `components/ui/`. The palette is a warm
sambal red on paper cream; category chips use muted tints. Small buttons are
44px on a phone and 36px once there is a pointer — this product is used
one-handed in a kedai.

## Deployment

Netlify, building the Next.js app.

**Required before a deploy is actually usable:**

1. Set the six `NEXT_PUBLIC_FIREBASE_*` variables in the Netlify site
   environment. They are read at build time.
2. Set `OPENAI_API_KEY` in the Netlify site environment. It is read at request
   time by the route handler. Do not set `OPENAI_BASE_URL`.
3. Deploy the security rules (both files) with the Firebase CLI.
4. Enable Cloud Storage — see below.
5. Add the deployed domain to Firebase Auth's authorised domains.

### Enabling Storage

Uploads cannot work until this is done, and it cannot be done from this
repository:

1. Firebase console → **Build → Storage → Get started**, in
   `asia-southeast1` to match Firestore.
2. `npx firebase login --reauth` if the CLI credentials have expired.
3. `npx firebase deploy --only storage --project <project-id>`
4. `npm run verify:firebase` — the 13 skipped Storage checks should now run.
5. `npm run test:flow` — steps 4 and 5 should stop reporting BLOCKED.

## Not built, by design

- Payment collection. The launch price is stated on the landing page as RM39,
  and the page says plainly that nothing is being charged yet.
- Password reset, email verification, Google and social sign-in
- Scheduling or publishing to Instagram, TikTok, Facebook or WhatsApp
- Multi-restaurant accounts, team access
- Reading the uploaded menu file. It is stored, and the prompt is explicitly
  told its contents were *not* read, so nothing is inferred from it.
- Cloud Functions, analytics, push notifications
